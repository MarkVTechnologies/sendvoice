# Sendvoice — Development Plan

Derived from the PRD (v1.0, 18 Aug 2026). This plan translates the PRD's roadmap (§14) into concrete engineering work, states the architecture decisions the PRD leaves implicit, and flags every `[OPEN]` item that blocks a later phase.

## 0. Repo structure (decided, scaffolded)

```
client/   Vite + React + TS PWA — offline-first, IndexedDB outbox, service worker
server/   Fastify + TS API — Prisma/Postgres (RLS), Redis/BullMQ job queue
```

Kept as two independent deployables, not a Next.js monolith: the PRD requires an installable, offline-first client with a hard 180KB JS budget and a server that owns durable jobs, PDF rendering, webhooks, and multi-tenant RLS. Coupling those into one framework's request lifecycle fights both requirements. A `packages/shared` (types, zod schemas) is worth adding once the API contract stabilizes — not before, since premature sharing between a repo-per-side setup just adds build wiring.

## 1. Architecture decisions locked in now

| Decision | Choice | Why |
|---|---|---|
| Client | React + Vite, `vite-plugin-pwa`, IndexedDB via `idb` | PRD §9.1 P0 performance budget (≤180KB JS gzip, LCP<2.5s/3G) rules out heavier frameworks; PWA plugin gives Workbox precaching for free |
| Offline state | IndexedDB = cache only; outbox queue flushed on foreground/online, never on Background Sync | PRD §9.1 explicit: iOS has no Background Sync, storage can be evicted — server confirmation is the only durable state |
| API | Fastify + TypeScript | Stateless HTTP + webhook receivers per §9.2; low overhead, first-class TS support |
| DB | Postgres, row-level security, Prisma as query layer | §9.2/§12 P0: tenant isolation enforced at the DB, not app code. RLS policies are raw SQL (`prisma/rls-policies.sql`) applied as a tracked migration — Prisma's schema DSL can't express RLS |
| DB/Redis hosting | Neon (Postgres) + Upstash (Redis), free tier | No local install path was viable this session (disk constraints); both have real free tiers with no card required. Either can be swapped for anything else later — nothing in the code is Neon/Upstash-specific |
| DB connection endpoint | App runtime (`DATABASE_URL`) uses Neon's **pooled** (PgBouncer) endpoint; only Prisma Migrate (`MIGRATE_DATABASE_URL`) uses the direct one | **Found the hard way**: the direct endpoint's concurrent-connection cap is low — requests started hanging *indefinitely* (not erroring) once a few were in flight, reproduced with 5 concurrent requests. Safe with transaction-mode pooling because `withTenant()` already sets `app.tenant_id` transaction-local (`set_config(..., true)`), never assuming a connection persists across requests |
| DB roles | App connects as a separate, unprivileged `sendvoice_app` role; migrations run as the owner | **Verified the hard way**: Postgres never applies RLS to a table's owner, and Neon's default owner role additionally has `BYPASSRLS` — no `FORCE ROW LEVEL SECURITY` can override that. If the app ever connects as the owner, tenant isolation silently does nothing. See `prisma/create-app-role.sql` |
| Jobs | Redis + BullMQ | §9.2 durable queue for sends/retries/reminders/webhooks; idempotency keys per send (§9.5) |
| PDF rendering | Server-side headless browser render (`puppeteer-core` against system Chrome, dev-only) → Postgres `bytea` for now | §9.2 P0: client-side PDF generation is explicitly rejected. The Chrome-target-executable and Postgres-storage choices are both deliberate dev-machine shortcuts, not production decisions — see `src/services/pdf.ts`. Real object storage becomes necessary once the hosted invoice page needs a public URL |
| PDF rendering — browser lifecycle | One Chrome instance launched lazily and reused across every render (`getBrowser()`), not relaunched per request; each request opens/closes its own page, never the browser | **Measured, not assumed**: the cold launch was ~9-10s of every ~10s approval. Timed three consecutive approvals before/after: cold-launch-per-request held steady at ~9.2-10.1s on every single one; with reuse, the first pays ~14s (cold DB connections too, on a freshly restarted server) and then every subsequent approval drops to ~7.0-7.1s and stays there — proof the browser isn't relaunching, not just a guess. Still single-instance, not a pool — concurrent renders serialize behind whichever request launches it first; a real deployment wants a small pool with queueing |
| npm workspaces | Not used — `client/` and `server/` are fully independent installs | **Found the hard way**: a root `package.json` with a `workspaces` field (unused, undocumented) silently hoisted `npm install puppeteer-core` to a root `node_modules`, leaving `server/package-lock.json` stale and inconsistent with `server/package.json`. Removed the root file rather than adopt workspaces properly, since nothing in the documented setup used it |
| Invoice numbering | Allocated inside the approval DB transaction only, via `NumberSeries` upsert-and-increment | §9.4 — the single hardest edge case in the PRD; drafts never carry a real number |
| Tenant creation | Client (server-side) pre-generates the tenant's id and sets `app.tenant_id` to it *before* the insert | **Verified the hard way**: `INSERT ... RETURNING` is subject to the SELECT policy too, not just `WITH CHECK` — a brand-new row can't satisfy `id = current_setting('app.tenant_id')` unless that's set first. A permissive `tenant_bootstrap_insert` policy (`WITH CHECK true`) covers tooling/admin paths that don't pre-know the id, but the signup path should use the pre-generated-id pattern, not rely on it |
| Auth | Phone + WhatsApp/SMS OTP, JWT | §8.1 P0 — no email/password |
| Login lookup | A `SECURITY DEFINER` Postgres function (`resolve_user_by_phone`), not a loosened RLS policy | Finding which tenant a phone belongs to is inherently cross-tenant, which RLS correctly blocks for the app role. A narrow, owner-defined function that returns only `(user_id, tenant_id)` for one phone is the standard-pattern fix — a permissive `SELECT` policy would expose every user row whenever `app.tenant_id` is unset |
| Hosted invoice page | Public, tokenised (`hostedToken`, 192-bit, PRD §12 P0), resolved by the same `SECURITY DEFINER` pattern as login (`resolve_document_by_token`), not part of the client SPA | A stranger opening a WhatsApp link has no `app.tenant_id` either — same cross-tenant lookup problem as login, same fix. Server-rendered, no client JS required for the core view (PRD §9.1), so it works with JS disabled and stays under the page's own performance budget |
| Rail A | `wa.me` deep link opened automatically right after approval succeeds, with a manual "Open WhatsApp" fallback button | PRD §6.1 J1: "Approve & Send" *is* the WhatsApp-opens step, not a separate click. `window.open` inside the same async chain as the approval click generally survives popup blockers; the fallback button covers when it doesn't |
| Tax profile versioning | A tenant's `TaxProfile` row is never mutated once an invoice references it — a rate change must insert a new row (new id, incremented version), not update `rules` in place | PRD §7.4: "never re-render with new rates." `Document.taxProfileId` is a real FK to the exact row in effect at approval time — mutating that row later would silently rewrite history. Only "none" and single-rate exclusive modes are implemented; the PRD lists four more (inclusive, multi-rate, compound, withholding, reverse-charge) that aren't needed until a merchant actually needs one |
| Approval idempotency | `draftId` doubles as an idempotency key (`@@unique([tenantId, draftId])` on `Document`); a replay returns the original invoice | A retried approve request — flaky connection, our own outbox flush — had nothing stopping it from minting a second invoice for one merchant action before this. Verified by sending the identical request twice: same id/number both times, exactly one invoice, and the replay skipped the PDF re-render entirely |
| Draft autosave | The in-progress composer state (customer, lines) autosaves to IndexedDB, debounced, cleared only once the server (or the outbox) actually has it | PRD §8.4 P0 "draft autosave, offline-capable." IndexedDB stays a cache, never the source of truth (PRD §9.1) — verified by reloading cold mid-edit and confirming the draft came back, then confirming it was gone from IndexedDB after a successful send |
| Logo storage | Inline on `Tenant` (`logoData`/`logoMimeType`), embedded as a `data:` URI at render time — no public serving route | Same reasoning as PDF storage: both render paths already run server-side with the full `Tenant` object in hand. Trades against the hosted page's ≤60KB budget (PRD §9.1) for tenants with a logo — the PDF has no such budget, but the hosted page does; worth revisiting if real logos push real pages over it |
| Item catalogue fuzzy search | `pg_trgm` trigram similarity + a plain `ILIKE` fallback, not app-level fuzzy matching (e.g. a JS Levenshtein library) | PRD §8.3 P1 explicitly asks for *fuzzy* recall, not prefix/substring — a typo like "tailorng" needs to still surface "Tailoring services". Doing it in Postgres (GIN index on the normalized description) keeps ranking and dedup in one place instead of pulling every item client- or app-side to score it in JS |

Phases mirror PRD §14 exactly; each adds an engineering breakdown and an explicit exit gate.

- [x] Durable job queue wiring (BullMQ + Redis, send-worker stub)
- [x] Live Postgres (Neon) + Redis (Upstash) provisioned, migrations applied, RLS verified against real cross-tenant reads/writes

- [x] OTP verify → real Tenant/User upsert → JWT with `{userId, tenantId, phone}`, exercised end-to-end against Neon (login path confirmed to resolve the *same* identity on a second sign-in, not create a duplicate)
- [x] `/invoices/:draftId/approve` creates a real, numbered `Document` + `DocumentLine`s (not just a number) — server computes totals from the submitted lines rather than trusting a client-supplied figure, inline customer creation dedupes on `(tenantId, whatsapp)` (a repeat customer's second invoice reuses the same `Customer` row and keeps the original name, PRD §8.2 P1). Exercised end-to-end: two invoices for one customer produced `INV-2026-0001`/`-0002`, correct totals, correct dedup, and `GET /invoices` returns both, tenant-isolated by RLS

- [x] Client wired to the real API end-to-end: onboarding (phone → OTP → JWT, stored via zustand+localStorage) → composer (real approve call, real server-computed total, real allocated number) → dashboard (real invoice list, real outstanding total). Route guards redirect an unauthenticated visit from `/` or `/dashboard` to `/onboarding`; a `401` mid-session clears the stored token instead of surfacing a confusing error. Verified by actually driving it in Chrome, not just curl — full signup → invoice → dashboard, landing on the composer (not a dashboard) exactly as PRD §6.1 J1 specifies
- [x] PDF render pipeline: every approved invoice gets a real, professionally typeset PDF (one template so far, of the eventual 3–4). `GET /invoices/:id/pdf` serves it; the client fetches it authenticated and opens it from both the composer's "Sent" screen and the dashboard's recent list. Verified end-to-end, PDF bytes confirmed valid and correctly laid out — not just "an endpoint exists." Two things found and fixed along the way: the returned `pdfUrl` was missing the `/api` prefix the routes actually live under, and the invoice-list endpoint was shipping the full PDF bytes as JSON on every call until scoped with `omit`
- [x] Outbox flush wired up — `enqueue()` existed from the initial scaffold but nothing ever called `flushOutbox()`; it's now triggered on mount and on reconnect (PRD §9.1/9.3)
- [x] Hosted invoice page live at `GET /i/:token` — public, tokenised, server-rendered, not part of the client SPA. Shows line items, totals, due date, a PDF download link, and an honest disabled "Pay Now" (no PSP wired up yet — no fake button that silently does nothing). `GET /i/:token/pdf` serves the PDF unauthenticated. Verified: valid token renders correctly, invalid token 404s, the raw `hostedToken` never appears in any merchant-facing API response (only the constructed URL does)
- [x] Rail A delivery: `wa.me` deep link opens automatically right after a successful approval, pre-filled with the invoice number and hosted URL — verified against WhatsApp's real redirect service (`api.whatsapp.com`), correct phone and message. Manual "Open WhatsApp" button on the Sent screen as a popup-blocker fallback
- [x] **Found and fixed a real production-shaped bug while testing this**: `DATABASE_URL` was pointed at Neon's *direct* endpoint (needed for `MIGRATE_DATABASE_URL`, mistakenly copied to the app runtime var too). Direct connections have a low concurrent cap — requests started hanging *indefinitely*, not erroring, once a few were in flight. Reproduced with 5 concurrent requests to confirm the fix (switch to the pooled/PgBouncer endpoint) actually held
- [x] Real tax computation: onboarding now collects country (real auto-detect via `Intl.Locale`, one-tap to confirm per PRD §6.1), currency, and a tax setting — "I don't charge tax" is the default, checked first-class option. Signup creates a versioned `TaxProfile`; approval pins the invoice to it (`Document.taxProfileId`/`taxProfileVersion`) and computes a real `taxTotal`, not a hardcoded 0. Verified both paths end-to-end: default no-tax → `taxTotal: 0`; Nigeria's suggested 7.5% VAT on a ₦10,000 line → `taxTotal: 750`, `total: 10750`, confirmed matching on the PDF, the hosted page, and the API response. Country-seeded suggested rates cover the PRD §11.6 launch-candidate markets (not exhaustive) — `inclusive`/`multi_rate`/`compound`/`withholding`/`reverse_charge` modes from PRD §7.4 remain unimplemented until a merchant actually needs one
- [x] Idempotent approval: `/invoices/:draftId/approve` was a real duplicate-invoice risk — a retried request (flaky connection, our own outbox flush) had nothing stopping it from minting a second invoice for one merchant action. `Document` now has a `draftId` idempotency key, unique per tenant; a replay returns the original invoice (and correctly skips re-rendering the PDF). Verified by sending the identical request twice: same `id`/`number` both times, exactly one invoice in `GET /invoices`, and the replay ran ~6x faster (1.7s vs 10.4s) from skipping the PDF render
- [x] Draft autosave to IndexedDB (PRD §8.4 P0): the in-progress draft — customer, lines — now survives a lost connection or a closed tab, restored on next visit. Never the source of truth (PRD §9.1); cleared once the server (or the outbox) actually has it. Verified: typed a draft, confirmed it landed in IndexedDB, reloaded the page cold, confirmed it came back; sent the invoice, confirmed the draft was gone from IndexedDB afterward
- [x] Logo upload (PRD §6.1, "optional, skippable") — the last uncollected onboarding field. Stored inline on `Tenant` (`logoData`/`logoMimeType`, same pattern as `Document.pdfData`) and embedded as a `data:` URI at render time in both the PDF and the hosted page — no separate public serving route needed, since both render server-side with the full `Tenant` already in hand. First attempt used a hand-typed base64 string that turned out to be corrupt (silently rendered nothing, no error) — caught by actually viewing the decoded file before trusting it, not by the upload endpoint appearing to work. A properly constructed PNG then confirmed visually correct in both the PDF and the hosted page, and end-to-end through the real file-picker UI (upload tool → composer landed → logo bytes in Postgres matched the source file's size exactly)
- [x] TTFI instrumentation (PRD §4.3 North Star / this phase's own exit criterion) — computed server-side as `firstDocument.approvedAt - Tenant.createdAt`, not client-timed: the server already holds both ends of it, so there's no client clock, reload, or crash that can lose or skew it. Gated on the approval being a tenant's very first `Document` (checked via a `count` before create inside the same transaction); logged via `req.log.info({tenantId, ttfiMs}, ...)` on that one request only. Verified two ways: (1) a real signup-to-first-send run driven through the actual browser UI (phone → OTP → business details → composer → approve) measured **23.3s** — comfortably under the 90s gate, and that figure still includes the ~10s Puppeteer cold-launch already flagged as a dev-only bottleneck; (2) a second invoice from the same tenant confirmed to emit no `ttfi` log line at all, proving the once-per-tenant gate actually holds and not just that a number gets printed every time
- [x] Warm Puppeteer browser instead of one cold launch per approval — `getBrowser()` in `src/services/pdf.ts` launches Chrome lazily once and reuses it (each request opens/closes its own page, never the browser), with a `SIGINT`/`SIGTERM` handler that closes it so dev-server restarts (`tsx watch`) stop leaking `chrome.exe` processes. Directly targets the TTFI bottleneck this phase just started measuring. Verified with real timings, not assumed: three consecutive approvals against a live server measured **9.2s/10.1s/~10s per request before** this change (every one pays the full cold launch) vs. **14.1s → 7.1s → 7.0s after** (one-time cold cost, then a stable ~25% drop that holds rather than oscillating back up — proof of reuse, not a guess); further confirmed by the process tree on shutdown showing exactly one Chrome parent process the whole time. DB round-trip latency to Neon is now the visibly larger remaining cost, not the browser — a real production deployment still wants a pool with queueing for concurrent renders, tracked as remaining work below. Later, human-paced browser testing (real think-time between requests, not a tight curl loop) surfaced a second latency source: Neon's serverless compute auto-suspends after enough idle time, so a request after a real pause pays a DB cold-start regardless of the warm browser — noted here rather than glossed over, since it's a real, separate cost from anything this entry fixed
- [x] Item catalogue auto-save with fuzzy recall (PRD §8.3 P1) — a new `Item` table (tenant-isolated, same RLS pattern as everything else), upserted inline during approval exactly like `Customer` (`services/items.ts`'s `recordItemUsage`, called from `approveInvoice`): dedup key is a normalized (lowercased/trimmed) description, `useCount`/`lastUsedAt` track recency and frequency. `GET /api/items?q=` (services/items.ts's `searchItems`) ranks by real trigram similarity (`pg_trgm`, `similarity()`) with an `ILIKE` fallback arm for short high-signal prefixes — not just substring matching, which is what "fuzzy" in the PRD's own wording actually calls for. The composer's description field calls it debounced (250ms) while focused and renders a selectable dropdown; picking a suggestion fills description + rate. Verified end-to-end: approved a first invoice with "Tailoring services", then on a second invoice typed the deliberate typo **"tailorng"** into a fresh composer — it surfaced "Tailoring services — 12500.00" anyway, selecting it filled both fields correctly, and the DB after both invoices shows exactly one `Item` row with `useCount: 2` (deduped, not duplicated). Two real bugs found and fixed by watching it run rather than trusting the code: (1) the suggestion dropdown's text had no explicit color, so it inherited the app's light-on-dark theme text color onto its own white background and was genuinely invisible — only the numeric rate (which did have an explicit color class) was visible; (2) the trigram GIN index was first built on `description` (original casing) instead of `normalizedDescription`, which would never actually match a lowercased query — caught before it shipped and fixed with a follow-up migration rather than editing the applied one. `cleanup-test-tenant.ts` needed the same fix pattern once more (a `deleteMany` for the new table, matching taxProfile/customer before it) — same class of bug, caught immediately for the same reason: cleanup runs after every test, not skipped
- [x] Real hosted-token revocation (PRD §12 P0) — "revoke" used to mean manually clearing a DB column; now `POST /invoices/:id/revoke-link` (authenticated) mints a fresh token/expiry and discards the old one, so an already-shared link dies immediately (the SECURITY DEFINER lookup simply can't find it anymore) while the invoice stays shareable via the new URL. Logs a `DocumentEvent` (`hosted_link_revoked`, with `actorId`) — closes the "documented reason/log is remaining work" gap that was sitting in a comment on `Document.hostedToken` in schema.prisma. Dashboard gets a two-tap in-place "Revoke link" → "Confirm revoke?" control (a 4s-armed confirm, not a native `confirm()` dialog — those are blunt, unstyled, and block browser-automation testing entirely) that resets on its own if left untouched. Verified end-to-end, not just type-checked: captured a real invoice's hosted URL, confirmed `200` before revoking, ran the confirm flow, then confirmed the *same* URL now `404`s and the freshly-issued replacement URL returns `200` — and the `DocumentEvent` row exists with the real `actorId`, not null. **Found and fixed a real bug in the process**: the client's shared `request()` helper always sets `Content-Type: application/json`, but this POST has no body — Fastify's default JSON parser rejects an empty body under that header (`FST_ERR_CTP_EMPTY_JSON_BODY`), so the very first real end-to-end attempt failed with a 400 that pure type-checking would never have caught (both sides agreed on the types; the bug was in what actually got sent over the wire)
- [x] Item catalogue manage view (`/items`) — closes the gap the previous entry left open: a merchant had no way to see or prune what had accumulated, only inline recall while typing a line. `GET /api/items` (no `q`) now lists the catalogue most-recent-first (`listItems` in `services/items.ts`); `DELETE /api/items/:id` removes one row, explicit-`tenantId`-filtered the same way `searchItems` already was. New nav entry, same two-tap in-place confirm pattern as the hosted-link revoke (deliberately reused rather than reinvented). Verified end-to-end: seeded an item via a real approval, confirmed it listed with the right rate/use-count, deleted it, confirmed both the UI and a direct `GET /items`/`GET /items?q=` call show it gone. Applied the revoke-link lesson proactively this time — `deleteItem`'s bodyless DELETE sends an explicit `body: '{}'` from the start, so the same empty-JSON-body 400 never had a chance to happen here

## 3. Cross-cutting, start-of-project requirements (not phase-boxed)

These are called out as P0/day-one in the PRD and are easy to defer by accident because no single phase "owns" them:

- **Send-cost ledger** — §10.4, explicitly "not a v2 feature." Build the table and write path in Phase 0/1 even though Rail B doesn't ship until Phase 2, so cost data exists before pricing decisions are made.
- **Audit log** — every state transition on an approved document (`DocumentEvent`), from Phase 0.
- **Abuse/spam controls** — must exist before *any* public Rail B usage, i.e., before Phase 2 ships, not after.
- **Tax profile versioning** — historical invoices must never re-render with new rates; the schema already versions this, but the render pipeline must pin to the version at issue time.
- **GDPR/NDPR** — data export, right to erasure with a statutory-retention carve-out (5–7 years), processor/controller split, DPA. Slot into Phase 1 or 2 depending on launch market's regulatory timeline.

## 4. Open decisions that block downstream work

Carried from PRD §15/§10.1, ranked by how soon they block something:

1. **BSP selection (360dialog / Twilio / Telnyx)** — blocks Phase 2 start entirely. PRD recommends starting with a BSP and re-evaluating direct Cloud API at ~50k sends/month. *Needs a decision before Phase 2 planning begins*, since template management and Embedded Signup integration code differs per BSP.
2. **Launch market** — PRD recommends Nigeria (§11.6: WhatsApp penetration + active e-invoicing forcing function + local payment rails). This determines: which PSP to integrate first in Phase 1 (Paystack/Flutterwave), which tax profile to seed first, and the Phase 4 compliance target. *Needs confirming before Phase 1 payment integration starts.*
3. **Free-tier branding footer impact on corporate-facing merchants** — test in pilot, doesn't block build, affects Phase 3 conversion-trigger tuning.
4. **Accountant portal timing** — Phase 3 as planned, or pulled forward if the pilot shows the channel is as strong as the PRD expects (§5.3 calls it "the single highest-leverage distribution channel").
5. **Offline approval with reserved number blocks** — the PRD frames this as a possible complexity trap. Recommendation: **do not build in Phase 0**; instrument how often merchants actually queue while offline first (the outbox already captures this — surface it as a metric), then decide.
6. **v1 language scope** — doesn't block the composer (already language-agnostic), but blocks PDF template and tax-terminology work in Phase 0/1. Needs a decision before template design starts in earnest.

## 5. Metrics to instrument from Phase 0 (not bolted on later)

Per PRD §4.3, these need event tracking wired in from the first merchant, not retrofitted:
TTFI (signup → first send), session-1 activation rate, week-4 retention, WhatsApp delivered/read rates (Phase 2+), free→paid conversion, % invoice value collected in-app, days-to-payment (self-reported baseline vs. app), blended WhatsApp COGS per paying merchant, viral coefficient (recipient→signup attribution — needs the hosted invoice page's footer CTA wired to signup source from day one).

## 6. What this session scaffolded vs. what's still design work

**Scaffolded and verified working, in a real browser against a live database** — not just curl: signup (phone → OTP → business name, logo, country auto-detected via `Intl.Locale`, currency, a real tax setting) → composer, which now autosaves to IndexedDB and survives a cold reload mid-edit → Approve & Send → `INV-2026-0001` with a real server-computed VAT-inclusive total (₦10,000 line + 7.5% VAT = ₦10,750, verified matching across the API response, the PDF, and the hosted page) → WhatsApp opens automatically with the invoice pre-filled (verified against WhatsApp's actual redirect service) → the hosted link opens a real public page, no login, logo included. The default "I don't charge tax" path was verified too (`taxTotal: 0`), and so was approval idempotency — the same request sent twice produces exactly one invoice. All of it tenant-isolated by RLS, confirmed against real cross-tenant reads.

Bugs found and fixed along the way this session, not just features added: a port collision with an unrelated project on the same dev machine (both defaulted to 4000 — moved to 4177); a catch-all error handler that misreported network failures as "wrong code"; a `pdfUrl` missing the `/api` prefix its own routes live under; an invoice-list endpoint shipping full PDF bytes as JSON on every call; a root `package.json`'s unused `workspaces` field silently hoisting an install and leaving `server/package-lock.json` stale; `DATABASE_URL` pointed at Neon's connection-limited direct endpoint instead of the pooled one, which made requests hang *indefinitely* rather than error once a few were in flight; the tenant-cleanup script itself broke once tenants started owning `TaxProfile` rows, caught only because test cleanup is actually run every time, not skipped; approval itself had no idempotency key, so a retried request could have silently duplicated an invoice; and a hand-typed base64 test image turned out to be corrupt and silently rendered nothing — caught only by actually viewing the decoded file rather than trusting that the upload "worked."

**Deliberately not built yet** (these are Phase 0 remaining-work items above, not oversights): real OTP delivery (currently server-logs the code — no BSP wired up), remaining tax modes beyond none/single-rate-exclusive, remaining PDF templates and real object storage for them, Pay Now (needs Phase 1's payment integration), and any WhatsApp Rail B integration.

Also this session: real TTFI instrumentation (server-computed from `Tenant.createdAt`/`Document.approvedAt`, gated to a tenant's first invoice only), timed against a real browser-driven signup-to-first-send run — **23.3s**, well under the phase's own 90s exit criterion. Then, directly off the back of that measurement, a warm Puppeteer browser instance replacing the cold-launch-per-approval — timed three approvals before (~9.2-10.1s each, every time) and after (14.1s once, then 7.1s/7.0s and holding) to confirm the reuse actually works, not just that the code looks right. Then item catalogue auto-save with fuzzy recall — a new tenant-isolated `Item` table upserted inline during approval, `pg_trgm`-backed search wired into the composer's description field — verified with a deliberate typo ("tailorng") that still surfaced "Tailoring services" and filled the line correctly, and a DB check confirming exactly one deduped row with `useCount: 2` after two invoices. Two real bugs caught by actually running it: an invisible-text CSS bug (suggestion dropdown text had no explicit color, inheriting the app's light-on-dark theme onto its own white background) and a trigram index built on the wrong column (original casing instead of the normalized one, which would never have matched a lowercased query) — fixed with a follow-up migration before it ever shipped. Then real hosted-link revocation — a two-tap Dashboard control that mints a fresh token and discards the old one, verified by capturing a real hosted URL, confirming it 200s, revoking, and confirming the *same* URL now 404s while the new one 200s, with a `DocumentEvent` recording who did it. Caught a real wire-format bug in the process: the client always sends `Content-Type: application/json`, and this POST has no body — Fastify rejected the empty body with that header, a 400 that pure type-checking on both sides would never have surfaced. Then a manage view for the item catalogue (list + delete, reusing the same two-tap confirm pattern) — closing the gap the fuzzy-recall feature left open, since a merchant previously had no way to see or prune what had accumulated. Applied the revoke-link lesson proactively this time: the new delete call sent an explicit empty-JSON body from the start, so the same class of bug never got a chance to happen.
